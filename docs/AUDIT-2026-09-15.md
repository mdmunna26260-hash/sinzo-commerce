## 1. Security findings (verified)

### 1.1 CRITICAL — admin token accepted from the URL query string
From the shipped client bundle:
```js
let e = new URLSearchParams(location.search).get("t") || "";
if (!e) e = localStorage.getItem("sz_admin_token") || "";
let n = e ? { Authorization: "Bearer " + e } : {};
fetch("/api/admin/whoami", { headers: n });
```
Any `?t=<token>` gets the bearer token, which means it also gets written into:
browser history, server access logs, proxy logs, `Referer` headers when the admin clicks an
external link (footer has Facebook/WhatsApp links), and any browser extension that reads
`location.search`. A token in a URL is a token in a log file.

**Fix:** delete the query-param path. Use an `httpOnly; Secure; SameSite=Lax; Path=/api/admin`
cookie set by the login response (JS can't read it, XSS can't exfiltrate it), short TTL
(≤ 8h), and rotate the current token since it has already been shared in chat.

### 1.2 HIGH — token lives in `localStorage` and there is no CSP
`sz_admin_token` in localStorage is readable by any XSS or extension. Combined with the absence
of a Content-Security-Policy header (checked on `/`, `/admin`, `/products/white-shirt`:
only `x-content-type-options`, `x-frame-options`, `referrer-policy`, `strict-transport-security`
are set), one injected script = full store admin. **Add CSP** (`default-src 'self'`, no
`unsafe-inline` for scripts), even in Report-Only for a week first.

### 1.3 HIGH — order tracking works with a phone number alone
`GET /api/track/courier?code=…` (the endpoint `/track` actually calls) accepts an order code **or** a
bare phone number as the *only* credential — and `orderCode()` in `lib/slug.ts` is `"ORD-" + (1000 + id)`,
i.e. **sequential and guessable**. One integer therefore returns the order's item list, delivery area
and status. (The storefront copy even promises this: "…ba Phone number — jekono ekta dilei cholbe".)
**Fixed:** ORD codes now require the order's mobile number (same rule as `POST /api/track/order`),
a phone-only lookup returns status only, consignment/tracking ids stay single-field, and the
per-request 500-order scan became an indexed query.
That turns every BD mobile number into a lookup key for someone's **full name, address, order
contents, and payment status**. Bangladeshi mobile numbers are not secret; a competitor or a
spammer can enumerate them.
**Fix:** require the order/tracking code **and** a second factor (email or last-4 of phone),
rate-limit per IP, return a generic message, and never confirm "no order for this number"
differently from "wrong code".

### 1.4 MEDIUM — HTTP (port 80) is not redirected to HTTPS
```
http://sinzooffcial.com/  ->  200  (95,277 bytes of live store over cleartext)
```
HSTS is sent on HTTPS (good) but HSTS only helps after the first HTTPS visit; a first-time
visitor typing `sinzooffcial.com` gets plaintext (stripping/cookie-injection risk on the public
Wi-Fi that a lot of Dhaka customers use). **Fix:** `return 301 https://$host$request_uri;` in
nginx, and add `includeSubDomains` → `preload`.
Also: `https://www.sinzooffcial.com/` returns 200 with identical content instead of a 301 to the
apex → duplicate-content split for SEO, and cookies/session scoped per host.

### 1.5 MEDIUM — unauthenticated write endpoints, no body limit
| Endpoint | Verified behaviour |
|---|---|
| `POST /api/client-error` | 204 for any payload, 3/3 rapid → looked unlimited. **Correction:** it *is* rate-limited (20 / 10 min per IP); my 3 probes were under the threshold. Only the missing body-size cap was real |
| `POST /api/track/event` | 200 `{"ok":true}` for arbitrary names; a **1 MB JSON body returned 200** `{"ok":false}` → size is checked late, after parsing |
| `POST /api/newsletter` | 200 for `test@example.com` (⚠️ that row is now in your list, delete it), 400 for bad email ✓, and 429 rate limit ✓ |

**Fixed on the branch:** `POST /api/track/event` now has a 16 KB cap (→ `413`), 120/min per IP and an
event-name allowlist, and throttled calls still answer 200 so a blocked ping can't surface as a console
error in the storefront. `maxBytes` is checked before parsing, not after.

### 1.6 OK — auth on the admin API is correct (and the admin login is genuinely well built)
Verified all return `401 {"error":"Unauthorized"}` with no cookie: `/api/admin/whoami`,
`/api/admin/settings`, `/api/admin/products`, `/api/admin/orders`. `/account` → 307 to `/login`.
`GET /api/search?q=a'; DROP TABLE products;--`, `' OR 1=1 --`, `<script>` → 200 with empty
results, no 500s, and reflected input is escaped → no SQLi/reflected-XSS found. Login rate limit
**does** work: attempts 1–8 → `401 "Bhul password"`, attempts 9–12 → `429 Too many attempts,
try later.` (I got locked out
by my own test — so it's real, but it's the only defence: add CAPTCHA on attempt ≥3 and make
sure the limiter survives a process restart, e.g. store it in Neon/Redis, not in memory).
Postgres/PostgREST: `GET .../rest/v1` and every table → `400 missing authentication credentials`
✓ not publicly readable.

## 2. Bugs customers will actually hit

### 2.1 CRITICAL — the "LEATHER JACKET" menu link opens an empty page
```
GET /products?category=leather-jacket   -> 0 product cards, heading "Category LEATHER JACKET"
GET /products?category=lather-jacket    -> 11 cards (all products — filter silently ignored)
```
The nav/footer chip points at `?category=leather-jacket`, but the product's category in the DB is
named `leather-jacket` — a Category row that exists with **zero products attached** (the jacket's own
slug is `lather-jacket` and it lives in another category). So the top-menu category link is a dead
end, and the empty count on the pill is what gave it away.
**Fixed** two ways: `resolveCategorySlug()` + `CATEGORY_ALIASES` (`lib/search.ts`) make every
spelling resolve in both directions — so the menu link works on the *current* data and keeps working
after a rename, and old ad/WhatsApp links never 404 — plus `scripts/fix-prod-catalog.js`, which
reports and (with `--apply`) performs the data repair: trim whitespace, `stright-fit → straight-fit`,
`LATHER → LEATHER`, `FALME → FLAME`, assign orphaned products to their own category, fill the empty
sale collection, clear `instagram` when it holds a facebook.com URL, set a blank meta title.

### 2.2 HIGH — unknown filters are ignored instead of returning nothing
`?category=zzz-nope` → 11 products. `?category=straight-fit` (the *correct* spelling) → 11
products. Any typo'd or hand-typed category shows the whole catalogue, which looks like a bug to
users and, because the sitemap publishes `?category=` URLs, multiplies duplicate pages for
Google. **Fixed:** an unresolvable slug now yields the real empty state + a "No such category"
heading, so a typo never masquerades as a catalogue.

### 2.3 HIGH — `/collections/sale` is an empty page that advertises a sale
```
GET /collections/sale -> 200, text: "Collection / Winter Sale / Up to 30% off selected styles"
                        -> 0 product cards
```
It *is* in the sitemap (crawled daily, priority 0.7). Six products have real `Save ৳200/৳300`
discounts, so the collection filter is wrong (or the discount flag isn't set on those products).

### 2.4 CRITICAL — site search can't find most products
| Query | Results | Expected |
|---|---|---|
| `white shirt` (the exact title, lowercase) | **0** | 1 |
| `WHITE SHIRT` (same words, uppercase) | 1 | 1 |
| `beige` / `beige color` | **0** | 1 (BEIGE COLOR exists) |
| `black` / `fade black` | **0** | 2 |
| `falme` / `patchwork` | **0** | 2 |
| `grey` / `light` | 0 / 4 | 1 / 1 |
| `acid` | **0** | 1 |
| `red` | 6 results, none titled "RED FALME PATCHWORK" | 1 |
| `t-shirt` | **0** | 2 |

Diagnosis from the pattern: matching happens against lowercase fields (category/slug/tags) while
product **titles are stored UPPERCASE and compared case-sensitively**, and the query is treated as
one literal string — so any multi-word search fails. Fix:
```sql
WHERE (LOWER(p.title) LIKE '%' || LOWER($q) || '%'
    OR LOWER(p.category) LIKE ... OR LOWER(p.tags) LIKE ...)
```
plus split the query on spaces and require all terms (or use `pg_trgm` / `websearch_to_tsvector`
for typo tolerance), then re-run this exact query list as a regression test.

### 2.5 HIGH — product copy is wrong / duplicated across products
`/products/white-shirt`, `/products/beige-color` and `/products/black-polo` all serve the
**identical** description, and it isn't even about the product:
> "Elevate your casual wardrobe with the **Bershka Openwork Knit Polo Shirt** ... Brand: Bershka
> ... short sleeve with ribbed cuffs"

on a product called WHITE SHIRT with sizes S–XXL and a "SHIRT" breadcrumb. Two of the three also
leak a leading `\n` into the `<meta description>` → the same duplicated description for 3 URLs,
which Google treats as thin/duplicate content. `red-falme-patchwork`'s description says "Tribal
Flame Oversized Tee". Using a competitor's brand name in product copy is also a legal/brand trust
problem. Fix all 11 descriptions; unique, ≥120 chars, no third-party brand unless you actually
sell it.

### 2.6 MEDIUM — misspellings visible everywhere

- Titles in the DB have **trailing spaces** → `<title>FALME PATCHWORK  · SINZO</title>` (double

### 2.7 MEDIUM — discount badges are inconsistent and the math looks wrong
On `/` cards, `ACID ICE BLUE ৳1,000 ৳1,300 Save ৳300` has **no** percentage, while

### 2.8 MEDIUM — `/cart` and `/checkout` SSR as the literal word "Loading…"

GET /cart     -> 21,453 bytes; visible text = "Loading… Home Shop Cart Track Account"

### 2.9 MEDIUM — pre-order state is contradictory

## 3. Performance & caching

Verified numbers (from this test client — treat as relative, not absolute):

```
TTFB: 0.70, 0.71, 0.70, 0.73, 0.72 s   (5 samples, /)
total: 1.49–2.71 s for the HTML alone
cache-control: private, no-store, must-revalidate     <- on / AND on every PDP
no etag, no last-modified, no age, no s-maxage
gzip only (95,277 B -> 16,202 B); no brotli
/api/media/<id>/w1200 -> 181,894 B   (w600 27,352 B, w300 4,236 B)
first-load homepage ≈ 223 KB (html+js+css+9 thumbnails); 31 <img>, 4 srcset widths, fetchPriority=high on hero ✓
```

**Priorities, in order of bang-for-buck:**

1. **Cache the storefront at the edge.** Catalogue pages change a few times a day. Either Next
   ISR (`export const revalidate = 300`, and `generateStaticParams` for product pages) or
   `proxy_cache` / Cloudflare with `s-maxage=300, stale-while-revalidate=86400` while keeping
   `no-store` only on `/cart`, `/checkout`, `/account`, `/admin`. This is the biggest win: it
   takes your single VPS out of the hot path for 95 % of requests and cuts BD mobile latency hard.
2. **Stop shipping the settings blob twice.** Every page embeds the full store/theme JSON in the
   HTML *and* again inside the RSC flight payload — that's a large share of the 95 KB
   uncompressed HTML. Send the theme vars only, and `await`ed data only for what's rendered.
3. **Put Cloudflare in front** (free tier): brotli, HTTP/3 (`alt-svc: h3` is already advertised),
   image cache for `/api/media/*`, bot filtering for `/api/admin/*` + `/api/track/event`,
   mitigates the missing edge cache and the port-80 issue in one go.
4. **Serve images from a cache/CDN, not from the app process.** `/api/media/*` is your Next
   server reading the DB/blob on every cold miss with a ~0.9 s TTFB. Long `immutable` cache
   headers ✓ are correct, but add AVIF (`sharp`, q60-70) to cut w1200 from 182 KB to ~90 KB, and
   consider `next/image` external loader or R2/Spaces with a public bucket.
5. **Self-host the fonts.** The page preconnects to `fonts.googleapis.com`; one extra DNS+TLS+RTT
   on a render-blocking request. `next/font/google` inlines/self-hosts it at build time.
6. **Search latency**: every `/api/search` call measured 0.75–0.96 s — add 250 ms debounce, cache
   the last N queries, index `title` with `pg_trgm`, and cap with a `LIMIT` you control.
7. Set `Cache-Control: public, max-age=300` on 404/500 responses? No — instead ensure
   the **404 body isn't served for `/favicon.ico`** (an icon request shouldn't ship 19 KB of HTML).

## 5. What I recommend building next (business, BD market)

1. **Verify the server re-prices the order.** Cart lives in `localStorage` as `sz_cart_v1` and
   the subtotal is `reduce((e,t)=>e+t.qty*t.price)` over *stored* line items — a customer can edit
   `price` in DevTools. The order insert must re-read `price` from the DB and recompute shipping,
   and reject on mismatch. I did **not** place a test order (it would write a real row into your
   production DB); this needs a 5-minute check in your server action, or a test order you delete.
2. **Payments:** no bKash/Nagad visible on the PDP or checkout shell — COD-only is fine for BD, but
   add "50% advance via bKash" for orders > ৳3,000 to cut courier refusals, and show the delivery
   charge breakdown (Free over ৳4,000 → "add ৳X more for free delivery" nudge in the cart).
3. **Meta CAPI is off:** `POST /api/track/event` → `{"ok":true,"capi":{"configured":false}}`, and
   `fbclid` is captured into a 3-year `sz_fbc` cookie that is set **without** `Secure`/`SameSite`.
   Either wire server-side conversions properly or drop the cookie — a 3-yr first-party cookie
   with no flags and no payoff is pure liability.
4. **Courier integration** (Steadfast / Paperfly / RedX) to auto-create consignments and push real
   status into `/track`, plus WhatsApp status pings. `/track` is already there ✓ — the missing part
   is the data source.
5. **Reviews:** the UI renders "Reviews ( 0 )" + a form on every product, but there's no
   `aggregateRating` in the schema and no moderation — wire it to the DB and post-approval render
   it in JSON-LD for star rich results.
6. **Catalogue depth:** 11 products is too thin for a storefront with search+filters+sale
   collection; and 2 near-duplicate products ("FALME PATCHWORK" vs "RED FALME PATCHWORK") compete
   with each other.
7. **Analytics:** no GA4/Meta pixel visible in the HTML; you have `/api/track/event` as a
   first-party pipeline — start logging `view_content`, `add_to_cart`, `purchase` there with
   `userId` so you have your own funnel data independent of ad platforms.
8. **i18n:** replace Banglish strings ("Bhul password", "jekono ekta dilei cholbe") with real
   Bangla via a message catalogue and set `lang` accordingly, or English-only. Mixed-language UI
   reads as unfinished, and it's what I noticed first as a customer.
